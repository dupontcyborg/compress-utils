# Benchmark note: decompress output sizing

Found during the libdeflate spike (worktree `compression-utils-libdeflate`, write-up in `docs/libdeflate-spike.md` there) and resolved in the harness on 2026-10-29. Related to `docs/benchmark-shortcomings.md`.

## The problem

The harness used to hand every decompressor an output buffer of exactly the original size, in one-shot, message-set and streaming modes. That is the best case and applies only to callers who already have the size. zlib, gzip and raw deflate do not record a usable output size (zlib has only an Adler-32, gzip's ISIZE is the last member's size mod 2^32, raw deflate has nothing), so a default binding streams them; libdeflate, which only has a whole-buffer API, was measured on a path our bindings do not take. The streaming mode also offered one output window the size of the whole file, which flatters inflate.

## The rule now

Nothing is told the output size. Each implementation uses what the compressed bytes record, or the library's own unknown-size API.

- **C one-shot and message sets.** A codec with a `size_hint` function (zstd, lz4 frame and snappy sizes, compress-utils through `cu_decompress_size_hint`, which succeeds for zstd, lz4, snappy and single-Stream xz but not for zlib, gzip, deflate, brotli or bz2) starts from the hint, capped at 1 GiB. Everything else starts from `3 x input`, with no minimum (1 byte only so an empty input works). The buffer doubles when the library needs more room, up to a 4 GiB give-up, and what happens then depends on the library's API. Whole-buffer-only libraries (libdeflate, libdeflate-percall, miniz, google-snappy, snappy-core) cannot continue, so they restart the decode from scratch with the doubled buffer. Libraries with a streaming API (zlib, zlib-ng, zlib-rs, ISA-L, liblzma, libbz2, libbz2-rs, brotli, zstd, lz4 frame, lzma-sdk and compress-utils) are driven the way a real unknown-size caller does it: all the input goes to the streaming decoder, and when the output buffer fills the harness doubles it with realloc, keeps the bytes already produced and continues, with no repeated work (`decompress_grow` in `bench_codec_t`). zstd, lz4 and xz use the streaming loop only when there is no hint; a usable hint goes to the whole-buffer call, and if a hint turns out too small the decode carries on in the streaming loop (or restarts, for a codec without one). The compress-utils loop is a stand-in for the core `cu_decompress_alloc` (stream API, 256 KiB input chunks, BUF_TOO_SMALL drain protocol); once that helper lands it should call it instead. The growth and restart cost is deliberately inside the timing. The physical buffer is kept between calls (and between the messages of a set), so malloc is not timed and, after the first pass, a growth step only raises the usable capacity. A message set recomputes the starting size per message. Records carry `decompress_size_hint` (`codec` only when the hint was usable on every call of the last timed pass, else `none`) and `decompress_retries`: the number of times the starting capacity was too small in the last timed pass (the whole set for message sets), a restart for the whole-buffer libraries and a growth step for the streaming ones, so it means the same thing for every row.
- **C streaming.** The input is fed in chunks (64 KiB by default) and the output goes into one reused window of `max(chunk, 64 KiB)`; each drained piece is passed to a sink that counts it. Verification is one extra, untimed decode whose sink compares against the original. In stream mode the record says `none`, since the hint is not used.
- **Python, Go, Rust, JS.** One-shot and message sets call the library's plain decompress with no size or capacity (no `expected_size`, `bufsize`, `output_len`, `max_output_size`, `DecompressWithCapacity`, `decompress_with_capacity`, `out` buffers). Streaming discards output as it is produced (Go and Rust through a fixed 64 KiB buffer). Python and JS drop each chunk as it arrives rather than reading through a bounded window, because those libraries expose none. Records carry `decompress_size_known: false`; they do not carry the C-only fields.

## What to expect

- Known-size formats (zstd, lz4, snappy) are unaffected.
- gzip's ISIZE is not used by anyone, in the harness or in our library: it is only the last member's size mod 2^32, a guess rather than a recorded size, so every gzip row starts like zlib and raw deflate. (libdeflate's own `gzip` program uses it; its library API does not. At the time of writing libdeflate's gzip decompress was only marginally faster than its zlib, which has no such hint.)
- On formats without a size (zlib, gzip, raw deflate, bz2, xz, brotli) the starting guess of `3 x input` is too small for anything that compresses better than 3:1, so the retry path is exercised by the repetitive file (xml, about 8:1); dickens (about 2.6:1), x-ray and the 4 KB messages fit. The multiplier decides how much a whole-buffer-only library loses: at 2x dickens misses and libdeflate's decompress drops from about 1.4x faster than ours to about 20% slower, purely from restarting. `BENCH_START_MULT` overrides it for a sensitivity check. Only the whole-buffer-only libraries pay for it with repeated work. The compress-utils rows follow whatever the library does for unknown sizes; once the core `cu_decompress_alloc` lands, the C driver's compress-utils codecs should call it for formats without a hint, which is the intended before-and-after comparison.
- Results from before this change are not comparable for decompress.
