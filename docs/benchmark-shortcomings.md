# Benchmark shortcomings

Known weaknesses of the ecosystem benchmarks (`benchmarks/`, results in `docs/ecosystem-benchmarks.md`), written against the current profile (2026-10-29): ten levels, `dickens` one-shot and streaming, `xml` and `x-ray` one-shot, `dickens` in 4 KB messages, run on a Mac and on two EC2 machines (c8g Graviton4, c8i Sapphire Rapids). These are candidates, written from knowledge of how the harness was built; verify each before acting on it. They are roughly ordered by how much they could change a conclusion. The point of this file is to say which conclusions to trust less.

Keep this lean: fix a shortcoming only if it threatens a decision we are about to make, and state the run-time cost first.

## Fixed since the first version of this file

- **Output sizes were handed to every decompressor.** Every driver now decompresses with no size: each implementation uses what the compressed bytes record (zstd, lz4 and snappy sizes, gzip's ISIZE, our own size hint) or its library's unknown-size API; in C, without a hint the buffer starts at `3 x input` (no minimum) and doubles on a miss: whole-buffer-only libraries (libdeflate, miniz, google-snappy, snappy-core) restart the decode, streaming-capable ones continue it, and both are timed. Records carry `decompress_size_hint` (`codec` or `none`) and, in C, `decompress_retries`. See `docs/benchmark-decompress-sizing.md` for the rule and what each driver does.
- **Streaming decompress had a whole-file output window.** C streaming now decodes into a reused 64 KiB window whose bytes are counted and discarded; verification is a separate untimed pass.
- **One machine, one architecture.** c8g (arm64) and c8i (x86-64, AVX-512) results exist, and they disagreed with the Mac often enough (CRC64 CLMUL, assert-enabled liblzma in the Rust and Go builds, the Python one-shot path) to find three real bugs in our own code.
- **One level in the headline tables.** All ten levels are run.

## Methodology

- **Thin corpus.** The profile is three files: `dickens` (text, ratio about 2.5 to 3.5), `xml` (repetitive) and `x-ray` (hard to compress). Streaming and the 4 KB message tier are `dickens` only, so they say nothing about binary or repetitive data. Missing: executables, already-compressed or incompressible data, very small messages (under 256 bytes), and realistic message corpora (logs, protobuf or msgpack, JSON API responses). Conclusions that rest on one file, or on text, are the weakest in the doc.
- **Samples are thin, with no variance reported.** Large files run 1 sample and 1 warmup, messages 3. The result JSON has medians and MADs, the doc tables show neither, and nothing pins processes to a core or randomises run order. Treat gaps under about 10% as ties. EC2 results come from one instance of each type on one day, so noisy neighbours are possible.
- **Level mapping is by hand, and speed is compared at a level, not at a ratio.** `benchmarks/levels.json` maps our levels onto each library's native ones by compression ratio (2% tolerance, checked by `check_levels.py`). Known problems: lz4 levels 1 and 2 are identical, zlib levels 8 to 10 are identical, xz level 9 maps to preset 8, ISA-L stops at level 3, snappy and bz2-compress are flat across levels. Where a competitor's levels cover a different ratio range, a per-level or geomean speed multiple is misleading: klauspost zstd tops out at ratio about 3.22 at about 31 MB/s, so its geomean "advantage" of 2.8 to 3.3 times is an artefact, and at equal ratio it is about 1.4 times faster than ours near our level 5. The scoreboard marks "comparable" cells (ratio within 5% of ours); a ratio-versus-speed curve for Go and Rust (`--sweep`) would settle the rest.
- **Some competitors are not like for like.** `ulikunitz/xz` has no levels and a lower ratio than ours at the same effort; lz4_flex, snap and klauspost's snappy have no levels, and klauspost's snappy encoder gets a better ratio than the C port. Compare those rows on decompression.
- **Competitor backends and variants are choices.** flate2's result depends on `miniz_oxide` or `zlib-rs` (we run both, not zlib-ng). Several C rows are variants of one library (libdeflate versus libdeflate-percall, libzstd-ctx, liblzma-fitdict), which flatters the library by showing its best configuration next to our default API.
- **The unknown-size policy is a harness choice.** A whole-buffer-only library that has to restart on a miss pays for the starting guess (`3 x input`), so the cost of the libdeflate and miniz rows depends on the ratio of the file (xml compresses far more than 3x); streaming-capable libraries grow the buffer and continue, and pay only the realloc (after the first pass, which only raises the usable capacity of a kept buffer). The retry count (`decompress_retries`, times the starting guess was too small) is in the record, and the policy is the same for every library, but another guess would give other numbers.
- **Bindings differ from C in two ways.** Python and JS streaming drop each chunk of output as it arrives rather than reading through a strict 64 KiB window, because those libraries have no bounded-output API; nothing accumulates, but the per-call output size scales with the ratio. The non-C records carry `decompress_size_known: false` and do not carry the C driver's `decompress_size_hint` and `decompress_retries` fields.
- **Sums over files hide the spread.** A tier's number is bytes divided by time summed over its files, so the larger file dominates. Per-file results are in the JSON but the doc does not show where we win on one file and lose on another.
- **Timing and thermal effects.** Wall-clock around the call, with warmup. The Mac was also in use. Later libraries in a long run may have run hotter.

## What is not measured

- **Memory.** Only the C drivers on Linux, by `benchmarks/memory.py` (see the README): peak resident set size of one compress and one decompress on dickens (one-shot and streaming) and on a 4 KiB message, minus the output written, in a fresh process per measurement. It counts touched pages only, so a large dictionary or table the codec never fills does not show; `malloc_trim` between the phases is glibc-only; the peak includes allocator slack and the codec's own input and output copies. No allocation counts, no per-context footprint when many contexts live at once, and nothing for Python, Go, Rust or WASM (where the heap is the constraint). The core `cu_decompress_alloc` keeps up to twice the output as spare capacity when it does not shrink; that trade is not measured either.
- **Concurrency.** Single-threaded only. No multi-threaded zstd, no free-threaded Python, no check of GIL release under load.
- **Latency distribution.** Throughput only. Tail latency and first-call cost are not measured; cold start only for JavaScript, as the median of 5 launches.
- **Browser.** Node and Bun stand in. Bun runs levels 1, 6 and 10 only.
- **Build flags.** Competitors are built from source by `deps.py` and we have not systematically checked that each got its recommended flags and CPU dispatch. The flags problem turned out to be real on our side (xz without `NDEBUG` or CLMUL in Rust and Go; fixed 2026-10-28), and the other codecs' assert settings in those builds were not checked.
- **No binary size or cold start for Go and Rust.** Only C (`size/size.py`) and JavaScript (`size/js_size.py`) have them.
- **Snappy streaming is not compared in Go and Rust**, because competitors' stream forms are framing formats, a different format from our raw blocks.
- **Platform libraries.** Python's `zlib` is the OS's library on the Mac and the distribution's on Linux, so deflate results for Python differ by machine.

## Language-specific gaps

- **Python** runs on 3.14 only, with competitors pinned to their latest at the time.
- **fflate streaming** is missing `sao` at levels 4 and up (see `docs/upstream-bug-candidates.md`), which no longer matters now that the corpus is three files, but check that the new files stream through it.
- **lz4js** output is invalid on three inputs, so its compress numbers describe work other decoders cannot read.
- **Go** runs against the stdlib, klauspost/compress, andybalholm/brotli, pierrec/lz4, ulikunitz/xz and dsnet/compress (archived); `DataDog/zstd` and `golang/snappy` are not included. **Rust** runs against flate2 (two backends), zstd, brotli, lz4_flex, snap, bzip2 and xz2; `ruzstd`, `lzma-rs`, `libdeflater` and the C `lz4` crate are not included.
- **Earlier Rust zstd and xz rows are superseded.** Runs of 2026-10-29 and before linked compress-utils and the `zstd`/`xz2` crates into one binary, so the linker resolved `ZSTD_*` and `lzma_*` to one copy and "ours" ran the competitor's C code (Rust ours xz decompress matched xz2 at about 95 MB/s, against 148 MB/s alone). Those two competitors are now separate binaries; re-run the Rust stage before using any Rust zstd or xz comparison (bz2 was not affected: the `bzip2` crate is pure Rust and exports no C symbols).

## Process

- **Nothing is in CI.** Results are committed JSON from manual runs, so a regression in our speed would not be noticed until the next run. The harness found three real regressions in our own bindings (a quadratic `memmove` in the xz stream, a missing CLMUL define, `NDEBUG` missing in the Rust and Go builds), so a cheap guard is worth having: one file, a few levels, our binding against our C core, failing if the binding is more than a set fraction slower.
- **Cost.** The full profile is long (roughly 4 to 5 hours per machine, an estimate, not measured). The slowest rows are brotli at top quality and xz at level 9; drop those cells on the extra files first if a run must be cut. Stages are independent and can be run separately.
- **Results age.** Competitor versions are pinned (`requirements.txt`, `package.json`, `deps.py`) and will go stale; the doc's numbers have a date but no rule for when to re-measure. Results from before the no-size-hint harness, the xz fixes and the Python one-shot change are not comparable with new ones.
